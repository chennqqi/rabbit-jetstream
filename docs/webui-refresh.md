# Read-page refresh and freshness

[English](webui-refresh.md) | [简体中文](webui-refresh.zh-CN.md)

An explicit `404` with error code `read_api_disabled` is not an ordinary availability failure. Overview and node readers clear that source's retained observation and local read time and show a disabled-read/authentication-configuration notice, matching the Queue/Stream list boundary. Other successful Overview sources remain independent. Generic 404 responses or the same code under a different HTTP status do not establish this condition. This does not erase user-entered route IDs, drafts or retained write evidence, infer credential expiry, or bypass server authorization; a subsequent successful authorized read can restore fresh observations.

The candidate Overview now implements the dashboard refresh requirement. It reads management/account info, declaration totals and configured-node monitoring as one concurrent read-only batch. This is not an atomic snapshot. After completion, the next batch starts after 10 seconds. A failed/invalid source or partial/unavailable monitored node increases the delay to 20, 40, then at most 60 seconds; a successful batch resets it to 10 seconds. A manual refresh replaces the pending timer and cannot overlap a running batch.

Hidden tabs schedule no new batches. A batch already sent may finish; hiding is not cancellation. Returning to the tab schedules one batch after the current delay, without catch-up bursts. Navigating away or leaving the authenticated view stops scheduling and cancels the view's readers; late results cannot restore cleared evidence. No editor, preview, mutation or audit-evidence request is automatically replayed by this scheduler.

While refreshing, the last successful panel value remains visible. Network/server/validation failure retains that value and its original local read-completion time, with an error and stale label. Authorization denial clears that source's protected values. A failing source does not erase successful siblings. Node monitoring retention is enabled in both Overview and the dedicated node pages.

An observation is marked stale while hidden, following a failed refresh, after 30 seconds, or when its read time is ahead of the local clock. The label updates while the page is open and on visibility changes. Time means local response completion, not broker sampling time or an atomic observation. The 30-second rule is a console freshness threshold, not a broker health/HA/qualification threshold. A clock adjustment can affect elapsed-age presentation; the underlying per-node source timestamps remain distinct evidence.

Settings offers manual/10/30/60-second preferences for Overview, Queue summaries, Queue/Stream lists and their Consumer collections, Stream configuration/state, node pages and standalone Consumer detail, defaulting to 10 seconds. The next delay uses the selected interval with the same 60-second failure cap. Manual mode disables periodic scheduling, not the initial visible read or explicit refresh. Switching intervals neither dispatches a new batch immediately nor cancels an in-flight batch. A view first opened hidden in manual mode reads once when first shown.

Only the exact selected number is stored under `rjs.overview-refresh-seconds`; malformed stored values fall back to 10. Storage failure keeps the choice in current page memory with an explicit unsaved warning. Clearing the session preserves this preference and language, not credentials or drafts. Another tab's storage changes do not live-update the current tab; reload reads the saved preference. The 30-second freshness threshold does not change with the refresh interval, so a 60-second choice can legitimately display stale observations between reads.

Consistent automatic refresh across other read pages, historical metrics and qualification evidence remain unfinished; this feature does not establish completion of those requirements.

## Queue Summary refresh

The Summary uses one concurrent batch for the declared Stream and the exact declared primary Consumer, not a Consumer list or priority aggregate. Both sources retain independent local read-completion times; the batch is not an atomic snapshot. The shared preference, hidden-tab pause, completion-based timing and capped failure backoff apply. Manual buttons select only their corresponding source, while both buttons share the batch's in-flight guard. The next automatic batch reads both sources again.

Loading and network/unavailable failures may retain a source's previous observation and original time, explicitly labeled historical; failed/hidden/older-than-30-second/future-clock observations are stale. Missing, denied, explicitly disabled or invalid responses clear only the affected source. Consumer missing is unknown, not zero backlog. No valid primary identity means no Consumer request and no fallback to a priority/list member. Navigation stops scheduling and fences late reads. Declaration, Plan, editor ETag, preview, mutation and audit windows are not polled or advanced.

## Standalone Stream configuration/state refresh

Stream detail now schedules its exact Stream GET independently from the Consumer collection. Both use the shared preference and freshness rules, but have separate single-flight guards, completion timers, backoff and read times; neither is an atomic snapshot of the other. Changing a Consumer query only replaces its collection reader/timer, without restarting the Stream read. Manual Stream refresh does not fetch Consumers and vice versa. Stream navigation/session exit cancels the old reader and timer and fences late success/failure responses.

Loading and unavailable failures retain the exact prior Stream configuration, counters, replica evidence and full response with original time and historical/stale notices. Missing, denied, disabled, identity/schema-invalid or unparseable JSON responses clear retained Stream values/time; successful collection rows remain independent. Invalid JSON is classified as invalid, not unavailable, for Stream readers including Summary and Consumer collections. Recovery replaces the observation without proving continuity across same-name recreation. No declaration, editor, preview, audit or mutation is refreshed.

## Queue and Stream list refresh

Refreshing an unchanged list query retains the last successful page and its original read-completion time while loading and after an unavailable/invalid response. A visible notice identifies rows, totals and pagination as historical results for that query, not current results. Detail links perform fresh reads. Successful refresh replaces the page and clears the notice. Changed search, order, offset or page size never reuses another query's rows; rejected queries, authorization failures and disabled read access clear prior data. Cancellation still fences late responses.

Queue/Stream lists now use the same completion-based read scheduler and Settings preference as Overview. Each resource/URL query owns its reader and scheduler; replacing it stops the old timer and aborts the old read. Automatic and explicit refresh share one in-flight guard. The scheduler repeats the submitted URL query, not unsubmitted search input or the returned page offset. Same-query refresh preserves the search input. Hidden tabs pause scheduling, and stale observations use the same 30-second/failed/hidden/future-clock rules. This list scheduler does not poll detail, editor, preview, mutation, Consumer or audit-evidence endpoints. The legacy preference key `rjs.overview-refresh-seconds` is retained so saved choices continue to apply; its scope is now explicitly shown in Settings.

Requested offsets remain distinct from server-returned page offsets. Queue/Stream lists and Queue Consumer lists preserve the original request offset when collection shrinkage clamps the response to its total. Refresh repeats that query; later growth must not silently redirect the request to the old clamped position. Pagination buttons use the observed page to choose an explicit new query. Filter/order/page-size changes retain their reset-to-first-page behavior. Deterministic tests exercise shrinkage, regrowth, repeated request offsets and explicit navigation for these models.

Verification covers single-flight batches, completion-based timing, capped backoff/reset, hidden-tab pause, thrown read errors, manual refresh, disposal and stale responses; retained values/timestamps and denial clearing have model tests. The isolated browser smoke waits for a real automatic refresh, injects one failed info response, checks retained value/time and successful sibling, then verifies manual recovery. It also runs the existing mutation safety regression. The injected failure is not a broker fault; the suite's separate broker-loss scenario remains in place.

## Node collection and detail refresh

Both node routes share the Settings preference and completion-based scheduler. Each route/Node ID has its own reader lifetime; navigation stops its timer, aborts the read and fences late results. One existing `GET /api/v1/nodes` supplies the configured-endpoint snapshot, not an invented per-node endpoint or discovered full membership. Partial or unavailable nodes trigger backoff even if the HTTP read succeeds. A successful empty configured-endpoint list is still not health proof.

Network/invalid-response failures retain the old snapshot and original read time, visibly labeling its nodes, identities and metrics as historical. 401/403 clear them. A new valid snapshot replaces the old one completely: missing IDs, changed IDs or duplicate ID matches cannot retain a previously selected detail. Failed individual sources do not inherit earlier metrics. Source times remain distinct from the page's local read-completion time. Hidden/failed/older-than-30-second/future-clock observations are labeled stale. The node scheduler does not add node actions or refresh Queue/Stream/Consumer detail, drafts, previews or audit evidence.

## Standalone Consumer detail refresh

The exact Consumer page uses the shared preference and scheduler, scoped to Stream plus Consumer name, without list enumeration. Same-identity refresh retains the prior observation/time while reading and after network/unavailable failures. Missing, denied, explicitly disabled or invalid responses clear the old observation; configuration and raw JSON are not exempt from that boundary. `durable` and `ack_policy` must be strings when present, so object-valued responses cannot reach React rendering. A new successful read can replace mode/counters, but does not prove continuity across a same-name recreation. Navigation cancels the old identity's reader/timer and fences late results. Hidden/manual/backoff/30-second freshness rules match the other supported pages. Queue Summary has its own batch described above; Consumer collections have their own query-scoped scheduler as described below. See [Consumer behavior](webui-consumer-detail.md#current-candidate-behavior).

## Consumer collection refresh

Consumer readers now treat JSON decoder failures as invalid responses, not ordinary unavailability. This applies to standalone Consumer detail, Queue Summary's exact primary Consumer and Queue Consumer collections, alongside the Stream readers. Malformed JSON clears the affected observation/page and original read time; a later 503 cannot resurrect data already cleared. Successful recovery restores fresh evidence. HTTP 401/403 still classify as denial even if the error body itself is malformed. Other sources and declaration/editor revisions are not refreshed or cleared by this classification.

The Queue Consumers tab and Stream's observed-Consumer collection now follow the shared preference. Only the submitted q/mode/order/offset/limit query repeats; unsent search input is not submitted or overwritten. Each route/resource/query owns one reader and completion-based scheduler. Changed query or navigation cancels the old read/timer. Requested offsets survive server clamping; explicit pagination chooses a new query. Model retention is opt-in and only for the same query: network/unavailable responses retain exact rows, totals, declaration revision (Queue only) and original read time with historical/stale notices. Missing, denied, explicitly disabled, rejected or invalid responses clear old data; a Queue declaration conflict also clears it. Invalid Queue/Consumer link identities are rejected before rendering.

Queue collection reads do not refresh the enclosing declaration or advance any editor ETag. A changed collection declaration revision remains distinct from the header revision and triggers the existing mismatch warning. Stream Consumer polling does not refresh the separate Stream configuration/state snapshot. Neither view presents these independent sources as atomic or invents healthy/zero aggregate counters. Actual broker loss retains explicitly historical Consumer rows and timestamps; this is different from a confirmed missing/denied response. Collection scheduling does not trigger Queue Summary, mutation, preview or audit polling.
