# 运维能力评审（技术经理视角）

[English](ops-review.md) | [简体中文](ops-review.zh-CN.md)

状态：评审完成，待排期 · 评审日期：2026-10-01
评审对象：管理服务（HTTP API）、运维 CLI（`rjsctl`）、管理控制台（`admin-ui/`）三层的**管理/运维功能完备性与可用性**
评审方法：
1. **三层盘点**——逐一枚举管理 API 全部 38 个端点（`management/internal/api/routes.go`）、`rjsctl` 全部子命令、控制台 14 个页面；
2. **场景实测**——本地真实服务（NATS JetStream + 管理服务 + 预置 6 队列/约 700 条消息/消费者）上演练值班场景：积压处置、DLQ、删除、诊断包、会话过期、审计排障；
3. **文档对照**——需求 backlog（`docs/webui-rabbitmq-requirements.md`，31 项）、各能力边界文档、随货告警规则（`deploy/observability/alerts.yml`）、指标暴露（`/metrics` 实测）。

视觉与信息架构问题不在本文重复，见[管理控制台产品评审](../admin-ui/design-review.zh-CN.md)。本文聚焦技术经理关心的三个问题：**功能齐不齐、好不好用、离生产闭环还差什么。**

## 1. 执行摘要

**这套管理面"能管好配置，管不了消息"——这是架构选择，不是缺陷，但必须被产品化地补齐。**

控制面采用"声明式队列生命周期 + 只读观测 + 消息数据面隔离"哲学：队列的创建/变更/删除走预览-确认-条件写，审计 intent/outcome 配对，消息操作被整体排除在管理面之外。在这个哲学内，交付质量是高的——声明式 CLI 工具链（`plan/diff/reconcile/apply`）、安全删除三层确认、诊断证据链在同类产品中少见。

但以"值班团队日常运营一个消息平台"的标准衡量，四个环节断链：

1. **消息级运维为零**（查看一条消息、清空、重放均不可能），所有数据面排障必须旁路到 SDK/CLI，而这条旁路没有任何随货工具或文档约定；
2. **告警链路不闭环**：随货 6 条 Prometheus 规则 + 控制台只读投影，但无 Alertmanager 配置、无通知渠道，控制台明确"不发送通知"——告警到人这一段完全靠部署方自建；
3. **一处 P0 稳定性缺陷**：未配置 Prometheus 时，告警监控路径空指针 panic 击溃整个管理进程（本轮评审真实发生，见 5.1）；
4. **发布工程脱节**：当前代码已漂移出 rc.2 冻结候选，文档状态滞后于实现（backlog 未回填、`management-api.md` 仍称 UI 为 read-only）。

分维度评价（5 分制）：

| 维度 | 评分 | 一句话 |
|---|---|---|
| 管理功能完备性（声明域） | 4.0 | 队列生命周期、批量、模板、导入导出、访问管理齐全 |
| 管理功能完备性（数据/运行域） | 1.5 | 消息级操作、消费者控制、连接管理、租户生命周期全部缺位 |
| 运维闭环可用性 | 2.0 | 告警不闭环、会话过期半死态、删除缺依赖方检查 |
| 自动化与 API 友好度 | 4.0 | API/CLI/控制台三层 parity 好，声明式工作流适合 GitOps |
| 安全与合规基线 | 3.5 | 密钥纪律、审计配对、脱敏诊断扎实；角色粒度粗、token 无轮换 |
| 可诊断性 | 3.5 | 诊断包/证据下载设计优秀；per-Queue DLQ 定位缺失 |
| 发布工程成熟度 | 2.5 | 证据绑定漂移、文档滞后、缺新冻结 |

**综合：3.0 / 5。** 结论：可以作为**声明式控制面**投入试运行，但必须同步交付一份"运营配套清单"（见 §7）并修复 P0，否则值班第一天就会撞上"看得到问题、没有任何抓手"的墙。

## 2. 运维能力矩阵

图例：✔ 已实现（控制台/API/CLI 至少一层可用）｜◐ 部分（有但有边界）｜✖ 三层皆无

### 2.1 已具备的能力（声明域强项）

| 能力域 | 内容 | 层覆盖 | 评价 |
|---|---|---|---|
| 队列生命周期 | 声明式创建/更新（条件写 + ETag CAS）、变更预检、导入导出、模板、批量变更（逐项确认）、CLI `plan/diff/reconcile/apply` | UI+API+CLI | ✔✔ 超越 RabbitMQ Management UI 的核心竞争力 |
| 安全删除 | 删除预检（消息/消费者计数、所有权）→ force 勾选 + 精确名 + 影响确认三层确认 → 证据 JSON 下载 → 不确定结局禁止自动重试 | UI+API+CLI | ✔✔ 安全设计示范级；缺 DLQ 依赖方检查（见 4.5） |
| 审计 | intent/outcome 配对、关联查询窗口（服务端过滤，实测生效）、导出 JSON、请求 ID 关联 | UI+API+CLI | ✔ 有 256 序号扫描窗口限制、无匹配总数 |
| 诊断 | 诊断包（9 端点元数据脱敏 ZIP、manifest+SHA256、有界任务、10 分钟过期）、CLI 同源 | UI+API+CLI | ✔ 实测创建到下载闭环可用 |
| 访问管理 | 本地账户 CRUD（argon2id）、OIDC PKCE 浏览器 SSO、operator/auditor 双角色、租户隔离、密钥不入 URL/存储/日志 | UI+API | ✔ |
| 备份与迁移 | `rjsctl backup create/verify/restore`（manifest+校验和）、`migrate` 五件套（RabbitMQ definitions 转换、双写 journal、影子捕获、对账、幂等切换/回滚） | CLI | ✔ 开箱即得的 RabbitMQ 迁移工具链是差异化亮点 |
| DLQ | 控制器自动搬运（at-least-once、`Nats-Msg-Id` 去重）+ 只读诊断视图（六类证据）+ 证据下载 | UI+API | ◐ 计数器是进程级全局累计，无法定位单队列（见 4.3） |
| 监控指标 | `/metrics` 暴露 22 组指标，含 **per-Queue** messages/bytes、controller、DLQ 计数、HTTP 指标 | API | ✔ 但无投递/消费速率、连接数、副本 lag |
| 告警 | 随货 6 条 Prometheus 规则（JetStream 不可用/控制器停摆/节点不可用/DLQ 失败/积压 10 万/管理 API 错误率）+ 控制台只读投影 | API+UI | ◐ 无通知闭环（见 4.2） |
| 实时事件 | SSE（租户隔离、认证、256 重放窗口、预算限制）驱动列表失效刷新 | API+UI | ✔ |

### 2.2 缺失的能力（数据/运行域缺口）

| 缺口 | 业界对照（RabbitMQ Management UI） | 影响场景 | 状态 |
|---|---|---|---|
| 消息级操作：查看/浏览消息、清空队列、单条重放/删除 | Get Messages、Purge Queue | 数据排障、测试环境清理、毒消息处理 | WEB-029/030 P2，架构明确"管理面不进数据路径"，需单独决策 |
| 消费者控制：暂停/恢复、重置 ack 偏移、删除消费者 | Consumer 管理（部分） | 积压处置、消费者迁移 | ✖（消费者创建本就在 SDK 域，但"观测到问题后无任何抓手"） |
| 连接管理：查看全库连接、断开客户端 | Connection 页 + Close | 客户端故障隔离 | ◐ 有精确 CID 查询与订阅明细（WEB-019 已做），无断开动作 |
| 租户生命周期：创建/修改/停用租户 | vhost 管理 | 多租户运营 | ✖ 仅 `RJS_TENANTS_FILE` 静态文件，变更需改文件重启 |
| Exchange 独立管理 | Exchange CRUD | 绑定治理 | ✖ bindings 只作为 Queue 声明的一部分（架构映射如此） |
| 告警通知 | 需自建（RabbitMQ 亦无内建） | 告警到人 | ◐ 需部署方配 Alertmanager；无 webhook/事件外送 |
| 备份恢复编排 | 插件 | 定时备份、演练 | ◐ 仅 CLI，无调度/无恢复演练文档 |

**技术经理结论**：声明域"齐"，运行域"缺"。这些缺口多数有明确的架构理由（管理面不进数据路径），真正的问题不是"没做"，而是**没有给运维团队交付替代路径**——旁路工具（SDK 脚本/nats CLI 用法）、文档约定、配套组件清单都缺。

## 3. 值班场景演练（好不好用）

以下场景在本地真实服务上逐一手动走查（桌面 1440，中英双语）。

### 场景 1：消费者积压（orders 队列待投递 500）
- **发现**：✔ 列表与详情大数字可见；随货规则 `RabbitJetStreamQueueBacklogHigh`（>10 万条持续 15 分钟）——但默认阈值对本例不触发，500 条积压**不会产生任何告警**，只能靠人看页面。
- **处置**：✖ 控制台无任何处置动作（无暂停消费者、无重投、无扩容提示）；Consumer 详情有积压诊断提示但只给结论不给动作。
- **实际出路**：修消费者端应用；用 SDK/nats CLI 查看消息。**旁路工具无随货交付。**

### 场景 2：死信处理（dead-letters 队列 7 条）
- **发现**：✔ DLQ 诊断视图提供目标声明/Stream/控制器状态六类证据。
- **处置**：✖ 明确不做重放/搬移/确认（文档边界）。重放必须 SDK 自写。
- **附加障碍**：DLQ 计数器（`rjs_dlq_*`）是进程级全局累计，**无法回答"哪个队列的死信失败了"**；告警 `RabbitJetStreamDeadLetterFailures` 也只能报"全局有失败"。

### 场景 3：删除队列（实测走完全程）
- **体验**：✔ 预检（所有权 matching/消息 0/消费者 1）→ 三层确认 → 证据下载，全程 5 步、防误删扎实。
- **缺口**：✖ 预检**不检查 DLQ 依赖方**——若有队列 A 的死信目标是 B，删除 B 无任何警告，A 的死信搬运会开始失败（只能事后从全局 DLQ 失败计数发现）；不确定结局（审计 503）后"人工排查"没有随货 runbook。

### 场景 4：诊断包（实测创建并下载）
- **体验**：✔ 创建 → manifest 表格（5 个源文件）→ 两步下载，30 秒完成；内容脱敏、排除消息与凭据，边界声明清晰。
- **摩擦**：两步下载 + "Server completion does not prove the browser saved the file" 免责句；任务重启即丢、10 分钟过期（对跨班次交接不友好，建议注明"先发给人再过期"）。

### 场景 5：会话过期（实测发生）
- **现象**：✖ Token 过期后页面退化为半死态：主导航消失、无重新登录入口，显示一段要求用户"自行记录证据再清除会话"的长文案，并把编辑器草稿的内部 JSON（`{"name":"","subjects":"",...}`）直接渲染在页面上。用户必须恰好知道点顶栏"清除本机会话"。
- **影响**：值班中 token 过期（默认 15 分钟 TTL）是高频事件，现在的处理方式是可用性事故。

### 场景 6：审计排障（实测）
- **体验**：✔ 关联查询窗口的服务端过滤真实生效（实测 `resource=orders-primary` 精确返回 4 条，带 filter 回显）；前端还有二次校验，服务端返回不符合筛选条件的数据会直接报错而非展示错误结果——工程质量好。
- **摩擦**：◐ 单窗口最多扫描 256 个序号、无匹配总数（防大海捞针的代价是"没有 404 到更早记录"的确认感）；导出 JSON 需手动两步。

## 4. 关键决策项（技术经理需要拍板的）

### D1｜P0：未配置 Prometheus 时管理进程会崩溃
- **事实**：无 `RJS_PROMETHEUS_URL` 的部署中，登录浏览数分钟后管理服务 panic 退出，栈顶 `management/internal/prometheus/alerts.go:49` ← `management/internal/api/events.go:227`（告警 watcher 空指针）。本轮评审中真实发生；指向不可达地址时不崩溃（走错误路径）。
- **决策**：立即修 nil guard + 回归测试（工作量小时级）。在修复合入前，任何部署都必须显式配置 `RJS_PROMETHEUS_URL`。

### D2｜消息级运维的架构决策不能再拖
- WEB-029（消息诊断）/WEB-030（purge/replay/retry）标记 P2"需单独架构批准"已有时日。这不是 UI 缺页面，而是**运维模式缺口**：没有它，"毒消息清理、测试数据重置、死信重放"三个日常操作全部依赖手写 SDK 脚本，每个团队各写一份且质量不可控。
- **建议**：批准一条"独立于管理面的受控数据面工具"路线（SDK/CLI 形态、脱敏、审计钩子），或明确宣布"本产品永远不提供，运营必须自建"并写进运营手册——两个都比现在的模糊状态好。

### D3｜告警链路不闭环
- 随货 6 条规则只是"告警定义"，没有 Alertmanager 配置、路由、通知模板；控制台告警页明确不发送通知。DLQ 失败告警是全局信号，无法定位队列。
- **建议**：随货交付 Alertmanager 基线配置（webhook/邮件示例）+ per-Queue DLQ 指标（`rjs_dlq_failed_total` 加 queue 标签或新增按队列计数）。

### D4｜会话过期态半死
- 过期后无导航、无重登入口、渲染草稿 JSON（见场景 5）。**建议**：过期时保留导航 + 显示"重新登录"主按钮 + 隐藏草稿细节。

### D5｜删除安全模型补最后一环
- 删除预检补 DLQ 依赖方检查（哪个队列声明了 deadLetter 指向它）；不确定结局场景提供一页 runbook（查什么、问谁、怎么取证）。

### D6｜发布工程卫生
- 当前代码已新于 rc.2 冻结候选，100 万消息压测、24h soak、100k Consumer 证据分属**不同 revision 与硬件**；`docs/management-api.md` 仍称 UI 为 read-only；backlog（WEB-017/022/024/026 已实现）状态未回填。
- **建议**：发布 rc.3 前重做 exact-candidate 冻结 + 回归；文档状态一次性对齐（半天工作量）。

## 5. 稳定性与安全观察（本轮实测）

1. **P0 panic**：见 D1。
2. **角色粒度**：仅 operator/auditor 两个固定角色，operator 同时持有队列写、诊断、审计、`access:manage`——没有"只管队列不碰账户"或"只读审计的值班员"细粒度。团队超过 5 人后会成为权限摩擦点。
3. **Token 管理**：`RJS_ADMIN_TOKEN` 是静态环境变量、无过期（`expires_at: null`）、无轮换机制；本地账户 token 15 分钟 TTL 合理。建议提供 token 过期与轮换路径。
4. **做得好的**：密钥不入 URL/存储/日志（实测 token 仅内存）；本地账户 argon2id；审计 intent/outcome 配对含失败尝试；诊断包脱敏并排除消息与凭据；租户级连接池与隔离。

## 6. 自动化与 IaC 就绪度

- ✔ OpenAPI 规范公开（`/api/v1/openapi.yaml`），Go/TS 两侧类型代码生成已接（oapi-codegen / openapi-typescript）；
- ✔ CLI 声明式工作流（`queue plan/diff/reconcile/apply/delete`）可直接支撑 GitOps：声明文件进仓库、CI 跑 `diff`、审批后 `apply`——这是同类产品少见的成熟度；
- ✔ 三层（UI/API/CLI）能力 parity 好：控制台没有"只有页面才能做"的操作；
- ✖ 无 Terraform provider / Kubernetes Operator 集成（队列声明无法进 IaC 体系）；
- ✖ 无事件 webhook 外送（告警、审计变更只能拉不能推）；
- ⚠️ 备份/迁移是单机 CLI 工具链（文件 journal、本地锁），服务化/调度化需自建。
