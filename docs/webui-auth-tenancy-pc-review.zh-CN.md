## 认证边界

`Authorization: Bearer` 只是一种传输机制，并非本身禁止。当前安全规则禁止凭据进入 URL、日志、提交文件和浏览器可读的持久存储。手工静态 Token 输入应只作为明确标注的恢复／引导入口保留。

不建议本管理后台采用常见的“账号密码登录后把 JWT 存 localStorage”方案：一旦页面脚本注入成功，攻击代码可以读取并长期带走 Token。推荐的正常登录方式是：

- `POST /api/v1/auth/login` 仅通过 HTTPS 接收账号密码，失败始终返回通用信息；
- 密码使用有界参数的 Argon2id 哈希，不可恢复明文；
- 成功后设置短时效、host-only、`HttpOnly; Secure; SameSite=Strict` Cookie；
- 写请求必须校验 Origin，并携带与会话绑定的 CSRF Header；
- 登录、限速失败、退出、会话到期和管理账号变更均审计，但不记录凭据；
- 静态 Bearer Token 作为独立且显式标注的应急／API 凭据继续保留。

即使 Cookie 由服务端签名且不存逐会话数据库记录，这仍然是服务端认可的会话。实现前必须确定密钥轮换、撤销、超时、多副本一致性、暴力破解限制和恢复流程。

## 多租户边界

租户是授权和数据源边界，不是 UI 筛选条件。所有请求、缓存键、后台刷新、诊断任务、审计事件、幂等键和 JetStream Client 都必须带租户作用域。用户必须具有明确的租户成员关系及租户内角色。跨租户反向测试必须覆盖直接 API 路径、旧页面模型、并发标签页、下载、审计查询和写入重放。

仍有两种本质不同的架构：

1. **一个管理服务连接多个租户。** URL/API 携带不可变 tenant ID，后端解析租户专属 NATS 凭据和服务集合。可提供统一控制台与真实租户切换，但会显著扩大凭据存储、连接池、缓存隔离、审计、限流和故障隔离的复杂度。
2. **每个租户独立部署管理服务。** 由反向代理选择租户实例，每个实例只持有一个 NATS Account 及其凭据。隔离最强、实现最简单，但不能在应用内切换租户，部署数量更多。

如果产品要求应用内多租户切换，就意味着选择方案 1。编码前必须批准租户来源、用户／成员关系存储、凭据来源、URL/API 兼容策略及迁移行为。

## PC 端整改

- 宽度超过 1,100px 时，把搜索、排序、每页数量和刷新组合成紧凑网格／工具栏；保留可见标签，让搜索框占弹性列。
- 普通输入框、下拉框和按钮限制为有效宽度，不再全部拉满面板。
- 把结果数、最后成功时间和分页压缩到表格头／尾，空状态靠近筛选区。
- 顶栏身份与会话操作合并到账号菜单，“清除会话”等破坏性操作放入菜单内部。
- 小于断点时保留现有移动堆叠，不以缩小触控目标换取 PC 密度。
- 混合版本部署时，后端不支持 OIDC 引导应视为“SSO 不可用”；只有识别到已配置契约但执行失败时才显示错误。

## 实施前必须确认

正常登录／会话模型与多租户部署模型应一起批准。推荐基线：内置账号密码 + HttpOnly Cookie，静态 Bearer 只用于恢复/API；如果要求应用内租户切换，则采用单服务、租户作用域 URL/API。

## 负责人决策与实现

负责人随后批准了不同的正常登录传输方式：内置本地账号密码认证返回短时效 Bearer Access Token，UI 只将其保存在页面内存，并在每个 API 请求的 `Authorization` Header 中携带；不得写入 `localStorage`、Cookie 或 URL。静态 Bearer Token 继续作为独立的恢复／自动化路径。该后续决策取代上文的 Cookie 建议。

获批的租户模型是单服务、多连接方案。当前实现使用显式租户浏览器 URL 与 `X-RJS-Tenant`，在访问后端前验证成员关系，并隔离 NATS 连接、监控、控制器、Consumer 索引、诊断任务所有权及审计存储。参见[本地账户认证](local-auth.zh-CN.md)与[管理面多租户](multi-tenancy.zh-CN.md)。
