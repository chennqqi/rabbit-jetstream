# 全局 Consumer 检索设计提案

[English](webui-global-consumers.md) | [简体中文](webui-global-consumers.zh-CN.md)

状态：负责人已批准推荐的实例内代次模型。有界采集器、受权 API、全局导航/列表界面和真实服务 Chromium 验收已经实现。目标规模性能测量仍待完成。

## 后端实现进展（2026-09-11）

`GET /api/v1/consumers` 只查询不可变的完整代次，绝不会发起 broker 枚举。`POST /api/v1/consumers/refresh` 是仅 operator 可用的显式刷新；并发刷新会合并。采集使用 16 个 worker、30 秒期限，并强制限制 10,000 个 Stream、100,000 行和 128 MiB 编码列表行。这些是与约定规模相符的安全预算，不是性能达标证据。

采集器会在完整 Stream/Consumer 遍历前后读取声明。只有所有来源成功且声明身份/修订未变化时才发布。失败不能替换完整代次；旧代次会明确标为 stale。没有完整代次时，读取返回 unavailable/collecting，而不是成功的空列表。Stream 缺失时仍保留预期 Consumer；观测到的外部 Consumer 以及不同 Stream 上的同名 Consumer 保持独立。精确零计数会保留，缺失观测使用 null 计数。

API、授权、代次冲突、完整合并、部分失败和声明变化测试已经通过。界面现在先展示列表，再提供稳定 URL 筛选、Stream/名称身份链接、模式/状态/排序/页大小控件、代次感知分页和显式 operator 采集。auditor 可以查询完整代次，但不能启动采集。无损解码会拒绝部分或误导性行。最终嵌入式 Chromium 证据为 `artifacts/webui-live-PI9GIr/report.json`：129 项检查和 24 个无障碍快照全部通过，其中包含独立的全局 Consumer 页面审计。这是样例规模的功能证据，不是 100,000 Consumer 的性能达标证明。

可重复的 [100,000 Consumer 算法原型](webui-global-consumer-scale.zh-CN.md) 现已执行实际采集与查询代码，并发现、消除了 100,000 个临时查询分配。在注明工作站上，优化后的 100,000 行扫描／筛选在八个单次样本中为 7.15–12.11 ms、22 次分配；完整内存 fixture 采集为 149.55–184.85 ms、约 258 MB 分配。真实 broker／UI p95 资格仍未完成。

## 需求与已核实缺口

WEB-021 要求按 Queue、Stream、durable 身份及状态进行服务端检索，先筛选后分页。既定规模目标为 10,000 Queue／100,000 Consumer；列表 API p95 ≤ 1 秒、首个可用列表 ≤ 2 秒需要绑定硬件和负载的测量证据，不能仅凭夹具渲染证明。

当前 `management/internal/api/handler.go` 只有 Queue 和 Stream 局部 Consumer 集合。`stream_consumers.go` 对单 Stream 完整枚举后筛选分页。`jetstream/client.go` 分别枚举 Stream 及每个 Stream 的 Consumer。`queue_consumers.go` 关联单 Queue 的期望／观测身份，有 2,000 项观测上限并复查声明修订。这些可复用，但不是现成全局索引。浏览器每翻一页调用它们，要么漏掉匹配项，要么反复枚举账号。

## 需要确认的方案

1. 推荐：实例内有界内存快照索引。查询使用不可变的完整采集代次，展示采集时间和过期／错误状态，不声称 broker 原子快照。实例重启丢失索引，需重新采集。不增加外部服务或持久化凭据／数据。
2. 每次请求实时枚举。保留状态较少，但每次全局筛选／翻页都可能遍历全部 Stream 和声明。资源变化会导致分页漂移；延迟及后端成本目标尚未证明。

推荐索引，是因为在目标规模下，反复全量扫描无法形成可信的低成本分页设计。方案尚未批准或实现。持久化索引、分布式缓存及账号切换不在本提案范围。

## 拟定正确性契约

- 范围为管理实例配置的 NATS 账号。沿用当前资源读取授权及本地演示策略；不新增订阅明文、客户端身份、凭据或任意元数据暴露。
- 规范身份为 `(stream, consumer name)`，不能仅用 durable 名称。不同 Stream 的同名项独立保留。Queue 关联须来自一致声明和受支持的归属检查，不猜测 `RJS_` 名称。
- 保留声明中期望但缺失的 Consumer，以及观测到的外部 Consumer。区分缺失、存在、不匹配及未知观测。持久 Consumer 没有客户端连接不能自动判故障；待投递／待确认数值不是根因结论。
- 采集可取消，每实例最多一个刷新在途，并限制工作线程并发及行数／字节／时间预算，超限明确报错。通过支持既定规模的原型测量选定具体预算，不通过截断为更小的方便数据集降低目标。
- 在独立临时结构中构建新代次，所有必需来源成功且一致性检查通过后才发布。失败／部分成功／超限刷新不能用部分数据或零总数替换完整代次。旧代次仅能以过期状态保留原时间戳及失败元信息；没有完整代次时返回不可用／采集中，不能返回成功空列表。
- 记录采集起止时间和代次 ID。多来源采集不是同一时刻的快照。采集中发现声明／身份变化则拒绝发布；观测后的变化仍可能发生。
- 对整个完整代次筛选，再按含身份次排序键的确定顺序排序，最后分页。默认每页 50，响应最多 200 项。返回筛选总数与代次 ID。请求固定的代次已不可用／被替换时，必须要求明确重置分页，不能静默混合代次；不无限保留历史代次。
- Go JSON 与浏览器无损解码器保持原始整数精度。只存储列表及关联必需字段，详细配置仍通过已有精确详情读取。
- UI 常规刷新低成本读取索引，不能每十秒触发账号全量扫描。明确区分采集刷新动作，合并重复请求并报告进度／失败。最终端点、方法、冷却时间在负责人确认与 API 审查后确定。

## 实施与验收顺序

1. 确认采集模型，定义强类型响应／查询契约及明确观测状态语义，通过原型测量确定预算。
2. 独立于 HTTP 实现采集／关联／查询，测试重复身份、外部资源、缺失声明／Consumer、归属冲突、取消、时间／行数／字节限制、部分失败、过期保留及并发刷新。
3. 增加有授权的 API 与 OpenAPI，拒绝未知／重复／畸形筛选、非法分页及代次不匹配。直接测试越权请求，并确保拒绝请求不启动采集。
4. 先提供真实全局列表再筛选，支持稳定 URL、按代次分页、显式刷新及精确详情链接。双语区分过期／不可用／空结果，不能把已有 Stream 页包装为全局检索。
5. 使用真实服务验证跨 Stream 的 201 项以上匹配、同名项、期望成员缺失、来源失败及代次替换；验证键盘／移动端和大整数。
6. 在明确硬件上测量 10,000 Queue／100,000 Consumer 的采集内存、broker 请求成本及查询延迟。未测量前不宣称达成绩效指标；发布／原生资格验收仍独立执行。
