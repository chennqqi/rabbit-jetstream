# WebUI 剩余门禁决策

[English](webui-remaining-gates-decisions.md)

状态：**已批准用于排期**（2026-09-12）。本文对 [WebUI 改进计划](webui-improvement-plan.zh-CN.md)遗留的决策与设施门禁作出裁决。本文授权排序与设施选型，不表示相应实现已经完成。

## 决策摘要

| 项目 | 决策 | 是否阻断首发 | 启动条件 |
|---|---|---:|---|
| F-4 全局 Consumer 归属 | JetStream 与 Queue 声明保持权威；管理服务只拥有按租户隔离、有界、可重建的读取投影，不成为新的事实源。 | 否；现有有界代次实现可用于首发。 | 扩展索引前，固化并测试多副本与陈旧语义。 |

| O-5 DOM 测试 | 选择现有 Node 测试运行器 + jsdom + Testing Library；交互使用 `@testing-library/user-event`。大范围 UI 重构前先完成。 | 是后续 UI 重构的设施门禁，不阻断已冻结候选版。 | 固定依赖版本，并提供一个确定性的路由/租户切换夹具。 |

| O-3 i18n 目录 | 与 F-8 解耦。产品文案由功能目录维护；OpenAPI 只能提供稳定错误标识，不能生成翻译正文。 | 否。 | O-5 已就绪，并明确目录命名和归属规则。 |

因此，本文取代改进计划中的原建议顺序。尤其是：O-3 不由 F-8 生成；O-5 提前到其需要保护的重构之前。

**执行更新（2026-09-13）。** 唯一负责人随后授权在本地完成全部顺序，并允许使用 Docker Desktop 模拟设施。F-7 因此在代理、重放、预算、背压及测试设施完成后提前执行；这只改变排期，不改变安全契约。本文范围内的实现/模拟证据现已全部关闭。精确候选的裸机、Canary 和外部签署门禁仍不在此范围内。

## F-4：全局 Consumer 投影归属

**决策。** 权威事实仍来自 JetStream 和租户的 Queue 声明。管理服务只拥有为读取优化的投影。该投影必须：

- 按租户隔离；
- 仅在一次完整采集成功后原子替换；
- 受 Stream 数、行数、字节数、并发数与采集时限的显式约束；
- 可丢弃、可重建；
- 可报告 `collecting`、`stale` 或 `unavailable`，但绝不能把不完整证据伪装成空的成功结果。

这与 `management/internal/api/global_consumer_index.go` 已存在的实现一致；本决策是将它正式固化，而不是引入持久化全局数据库。Queue 健康信息不得按展示行逐条读取；它只能来自有界采集/批量读取，或独立详情/诊断请求。

各管理服务副本可以持有自己的投影。因此，代次标识是副本本地证据，不是集群级版本。部署多副本前，分页会话必须使用粘性路由，或另行设计共享投影。代次不匹配必须继续显式返回 409/要求重置，不能静默跨代次继续。

## F-3：分页与有界枚举

**决策。** 不建立一个通用游标抽象后就宣称解决了全量枚举。游标可以约束客户端遍历并保持排序一致性，但不会让 `ListDeclarations`、`ListStreams` 或逐 Stream 的 `ListConsumers` 自动变成增量读取。

全局 Consumer 端点保留 `generation + offset + limit`。它已经具备快照身份、有界页面响应及明确的代次变化失败。未来可以用不透明游标编码这些字段，但这属于兼容性/UI 便利改进，不是扩展性修复。

Queue 声明和其他实时列表必须先形成数据源专属契约。每份契约都要定义稳定排序、最大扫描条目/字节/时间、并发变更行为、游标过期、租户与筛选条件绑定、非法游标错误，以及总数是精确值、估算值还是省略。v1 期间继续支持现有 offset 参数；除非另行批准 API 版本决策，否则游标只做增量能力。

10k 查询基准只测量内存过滤/排序。它是有效证据，但不能证明后端枚举或 100k Consumer 采集已合格。只有端到端规模与内存测试覆盖采集加分页后，F-3 才可关闭。

## O-5：DOM 测试设施

**决策。** 保留 `node --test` 作为运行器，新增固定版本的 `jsdom`、`@testing-library/react` 与 `@testing-library/user-event` 开发依赖。另引入 Vitest 会增加迁移与配置成本，却不能提供额外的必要能力。

首个夹具必须通过真实 DOM 事件运行 `main.jsx`，覆盖路由分发、浏览器 history、存在脏状态时切换租户（取消与确认）、权限/会话替换、焦点恢复以及卸载清理。网络和时间均注入，不使用真实 NATS。Playwright 继续作为浏览器集成、无障碍与截图的权威；DOM 测试是快速回归层，不取代 Playwright。

O-5 是第一项设施任务，因为 F-8/O-3 和 S-4 都会触及同一高风险组合层。

## F-8：OpenAPI 生成边界

**决策。** Go 模型使用固定版本 `oapi-codegen`，TypeScript 类型使用固定版本 `openapi-typescript`。初期只生成 Schema，把生成物提交到仓库，并在 CI 中重新生成后要求工作树无差异。生成器版本和命令必须单一来源；依赖安装后可以离线复现。

第一阶段不生成服务端路由，也不替换 WebUI HTTP 传输层。现有传输层负责认证、租户 Header、错误规范化、取消、下载，以及对超过 JavaScript 安全整数范围的计数值进行无损处理。只有具备等价测试后，生成客户端才可以替代它。

在将生成设为门禁前，先把 `api/openapi.yaml` 中待迁移端点的通用响应对象替换为具体 Schema。Go Handler 可逐步采用生成的响应模型；内部 JetStream/领域模型不得反向依赖传输层生成类型。

## O-3：完整 i18n 目录化

**决策。** O-3 与 F-8 是独立工作流。OpenAPI 描述协议字段和稳定错误码，无法拥有导航标签、操作说明、警告、空状态或无障碍文本。由 API 契约生成翻译 key 会制造错误耦合，也无法覆盖大多数界面文案。

采用功能级目录，并保持 `en`/`zh` key 结构完全相同。在现有一致性测试上增加缺失 key 与未使用 key 检查。用户可见的内联中英三元表达式按功能逐步移除；动态值和无需翻译的协议标识作为参数保留。完成标准覆盖两种语言下的正常、空、加载、陈旧、错误、确认和无障碍状态。

F-8 可以提供供目录消费的类型化错误标识，但两个任务互不等待，也不能互相标记完成。

## S-4：密度、共享表格与视觉 QA

**决策。** 只为语义一致的只读集合建立共享表格与分页基础组件。复杂证据表、对比表、可编辑表及嵌套表继续专用。共享组件必须保留原生表格语义、caption、可聚焦的横向溢出、陈旧/错误证据、精确/未知总数及链接行为。

组件抽取与密度调整同批提交，并由 DOM 覆盖保护。视觉验收使用完全相同的确定性数据，在 1440、1280、1024 与 375 CSS 像素下，覆盖中英文、明暗主题；至少包括正常、空、错误/陈旧、长标识符和最大列数场景。Chromium 作为截图基线；Firefox 执行溢出与焦点功能检查。任何截图差异都必须人工审阅，不能自动接受。

目标是在不裁切控件、不隐藏证据、不产生分页歧义、不降低键盘可用性的前提下提高信息密度。组件复用比例不是验收指标。

## F-7：带鉴权的服务端事件

**决策。** 实现继续延后至首发后，设施门禁通过前保留轮询。浏览器原生 `EventSource` 无法附加所需的 `Authorization` 与 `X-RJS-Tenant` Header；把 Access Token 放入 URL 或持久化存储也被禁止。因此客户端使用可取消的 `fetch` 请求，并解析标准 SSE 线格式。

首个事件流只读且按租户隔离。它可以承载审计尾部事件和触发有界刷新的失效提示；如果告警来源仍由轮询获得，则不能宣称告警精确投递。契约必须定义事件 ID、`Last-Event-ID` 重放窗口、心跳间隔、重连/退避、慢客户端缓冲策略、每 actor/租户/实例连接上限、服务端关闭行为以及 401/403/429/503 响应。

设施门禁包括：反向代理缓冲/超时、HTTP/2 行为、泄漏/背压测试、重连/重放测试与容量证据。长连接继续位于消息数据路径之外。

## 单负责人批准顺序

1. 固化 F-4/F-3 API 不变量，补齐代次/多副本契约测试；暂不重写分页。
2. 完成 O-5 DOM 设施及高风险路由/租户测试。
3. 加固所选 OpenAPI Schema，再引入 F-8 类型生成与 CI 漂移检查。
4. 独立迁移 O-3 功能目录，并使用 DOM 设施保护行为。
5. 实施 S-4 共享基础组件与密度调整，随即完成完整视觉 QA 矩阵。
6. 执行端到端规模验收；只在证据证明有必要的数据源上实现 F-3 专属游标。
7. 首发后先验收流式设施，再实现 F-7。

在只有一名负责人时，每一步采用“一份决策记录、一次实现变更、一组验收证据”，不设置委员会式的多段审批；但客观门禁失败时，该步骤仍不得晋级。

## 关闭证据

这些跟踪项只有具备以下证据后才可关闭：

- F-3/F-4：API 契约测试、代次失效测试、有界采集测试，以及 10k Queue/100k Consumer 端到端耗时与内存结果。
- O-5：覆盖上述路由/会话/租户路径的确定性 DOM 测试，且现有 Node 与 Playwright 套件通过。
- F-8：固定版本、可离线复现的生成流程，clean-diff CI、具体 Schema 与传输层等价测试。
- O-3：目录一致性、缺失/未使用 key 检查及双语状态覆盖。
- S-4：组件测试、无障碍检查，以及对完整矩阵执行过人工审阅的相同数据截图证据。
- F-7：代理验收、连接预算/负载结果、重放/重连/背压测试，以及认证与租户隔离测试。
