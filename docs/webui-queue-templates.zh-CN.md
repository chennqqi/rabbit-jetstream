当前内嵌 Chromium 证据 `artifacts/webui-live-b5ugik/report.json` 通过 132 项检查，使用已晋升的四文件内嵌 UI 和本机重建的候选管理二进制。批量场景创建两个隔离 Queue，在其中一个上制造真实 ETag 冲突，要求同时显示 `ready`／`conflict` 逐项结果，不为失败目标提供审阅动作；随后仅对就绪 Queue 重新读取、重新预览、独立确认并执行条件更新。导出场景还实际下载 `rjs.queue-change.v1` 更新包，核对精确 int64、标签及带引号 ETag，并验证离开面板后两个 Blob URL 均被回收。

## 有界批量更新预览后端

`POST /api/v1/queues/change-plan` 在严格的 4 MiB 封装中接受 1–100 个 `{document, etag}` 项，每份 Queue 文档上限为 1 MiB。每个唯一且有效的项目都携带原始带引号声明 ETag，在共享十秒期限内复用既有的仅更新预览。结果保持输入顺序，区分 `ready`、`blocked`、`invalid`、`conflict`、`missing` 和 `unavailable`；无效 ETag 与重复 Queue 身份会逐项报告，不会静默丢弃。单项失败不能把整个集合展示为成功，也不能隐藏其他项的成功预览。

该端点仅限操作员、严格只读，不记录变更审计事件。它没有提交、自动重试或回滚操作，也不表示原子性。WebUI 会核验完整响应，让操作员选择就绪目标，重新读取并匹配原始 ETag，再复用既有编辑器执行新的服务端预览和独立确认条件写入。保留的编辑器保存独立结果；系统刻意不提供“全部提交”。

创建表单提供三种本地模板：Subject Queue、优先级 Queue、带 DLQ 目标的 Queue。名称、Subject、副本、存储及正数消息上限仍须明确填写，并依据当前创建规则验证。不会悄悄代填推荐部署配置。准备草稿前可审阅生成 JSON，保留 int64 消息上限精度。

优先级模板从明确填写的 1–255 添加 `spec.maxPriority`。该模板请求实际优先级层次；显式零仍可通过普通 JSON 编辑器／导入契约使用。须在服务端计划中审阅生成的 Consumer 及资源开销，优先级不保证应用处理顺序。DLQ 模板仅添加 `spec.deadLetter.queue`，既不创建目标，也不证明其存在、兼容或转移健康。自引用在本地拒绝，目标和依赖链校验仍由服务端负责。投递默认值留给服务端预览解析。

切换模板时保留表单已填值，但生成文档仅包含所选模板的字段。不使用模板时恢复原创建行为。创建成功后“创建另一个 Queue”会清空整个表单，包括模板字段。模板复用已有名称保留注册及仅创建编辑器，不开辟替代写入路径。Schema 失败时禁止准备草稿，准备过程不发送 Queue API 请求。仍强制要求新鲜的服务端预览、明确确认及 `If-None-Match: *`。模板不能解除不确定写入，也不能覆盖已有资源。
