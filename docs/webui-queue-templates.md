## Bounded bulk-update preview backend

`POST /api/v1/queues/change-plan` accepts exactly 1–100 `{document, etag}` items in a strict 4 MiB envelope, with each Queue document limited to 1 MiB. Every unique valid item reuses the existing update-only preview with its original quoted declaration ETag under one shared ten-second deadline. Results preserve input order and distinguish `ready`, `blocked`, `invalid`, `conflict`, `missing` and `unavailable`; invalid ETags and duplicate Queue identities are itemized rather than silently dropped. A failed item cannot turn the collection into success or hide successful sibling previews.

The endpoint is operator-only, read-only and records no mutation audit event. It has no apply, automatic retry or rollback operation and does not imply atomicity. The WebUI validates the complete response, lets the operator choose a ready target, rereads and matches the original ETag, then uses the existing editor for a fresh server preview and separately confirmed conditional write. Retained editors preserve independent outcomes; there is deliberately no apply-all action.

The creation form provides three local templates: Subject-based Queue, priority Queue, and Queue with a DLQ target. Name, Subjects, replicas, storage and positive message-count limit remain explicit inputs validated against the current creation controls. No recommended deployment configuration is silently supplied. The generated JSON is available for review before preparing the draft, preserving exact int64 message limits.

The priority template adds `spec.maxPriority` from an explicit 1–255 input. This template requests actual priority levels; explicit zero remains available through the ordinary JSON editor/import contract. Generated Consumers and resource cost must be reviewed in the server plan. Priority is not a guarantee of application processing order. The DLQ template adds only `spec.deadLetter.queue`; it neither creates the target nor establishes its existence, compatibility or transfer health. Self-reference is rejected locally, while target and dependency-chain validation remain server responsibilities. Delivery defaults are left to the server preview.

Changing template selection preserves typed form values but includes only the selected template's fields in the document. Selecting no template returns to the original creation behavior. Successful creation followed by “Create another Queue” resets the complete form, including template fields. Templates use the existing retained-name registry and create-only editor, not an alternate mutation path. Schema failure prevents draft preparation; preparation performs no Queue API request. Fresh server preview, explicit confirmation and `If-None-Match: *` remain mandatory. Templates cannot resolve uncertain writes or overwrite existing resources.
