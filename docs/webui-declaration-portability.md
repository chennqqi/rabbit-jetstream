## Batch dependency planning core

The source API `POST /api/v1/queues/import-plan` now accepts `{"documents":[...]}` with existing operator/preview authorization and capability-precondition handling. The envelope is limited to 4 MiB and 1–100 items, each document to 1 MiB, names to 256 bytes. Unknown/repeated envelope fields and query parameters fail. Invalid items preserve their index and safe identity, preventing dependents from being misclassified as external.

External references are deduplicated and sorted, then read with a shared five-second declaration-lookup deadline. `external_declarations` distinguishes present, missing, unavailable and unrepresentable; a present item includes its exact source KV ETag. These observations do not clear the core's unverified-dependency problems: existence of a saved declaration is not live Stream ownership/health or apply authorization. Cancellation/deadline expiry returns 503 without partial evidence. The response contains no raw document/label/error text. Three API tests cover authorization, malformed/duplicate/oversized envelopes, indexed invalid items, deduplicated observations, exact ETag, no writes, cancellation and inconsistent target declarations. Batch UI and per-item target preview/apply remain pending.

`topology.PlanImport` is implemented as a pure, bounded calculation for 1–100 typed Queue documents and is now used by the source API above; the batch UI remains pending. It reuses `BuildPlan`, copies planner-sorted input slices and returns each original input index, Queue identity, content revision when valid, dependencies and projected problem codes. It does not return raw documents, labels or validation strings. It detects duplicate names, invalid declarations, actual dependency-cycle members and transitive blocked dependents. A reference outside the input set is `external_dependency_unverified`, **not** proof that the destination Queue is missing.

`order` contains only unblocked input indexes, dependency-first with deterministic lexical tie-breaking. An independent valid subset can have an order even when other items are blocked; `ready` is false in that case. Even `ready=true` only means internal declaration validity and ordering: destination existence, ownership, capacity, external dependencies and mutation preconditions remain unverified. No returned order authorizes applying a batch or implies atomic rollback. A destination-aware API, dependency observations, explicit per-item preview/apply and itemized outcomes are still required.

Five tests cover deterministic order across input permutations, cycle membership versus dependent blocking, invalid/duplicate/external prerequisites, the 100-item chain boundary, non-mutation and projection. Topology/API tests and topology static checks passed. No new executable/browser qualification is implied.

## Export contract

`GET /api/v1/queues/{queue}/export` returns a JSON attachment named `{queue}.queue.json`, using the existing versioned Queue Schema. It reads one saved declaration, verifies its identity and content revision, and requires faithful `QueueDocument` reconstruction. It does not guess missing provenance in old Plans. The normalized document may differ lexically from the original YAML but retains exact supported values, including large integers, explicit priority zero and DLQ references.

Resource-read authorization is unchanged: operator/auditor by default, with the existing explicit local-demo exception. Default export removes **all free-form labels**. `?include_labels=true` explicitly includes them; `false` is equivalent to omission. Redaction can change declaration content/revision. It does not hide Queue names, Subjects, binding keys or DLQ references, which may themselves be sensitive. Inspect the downloaded file before sharing it; no automated secret-free guarantee is made.

The body contains only the Queue document, not the saved Plan, runtime observations, authentication credentials or message data. Dependencies are **references only**: exporting a Queue does not export its DLQ target or prove that target exists. This is neither a message backup nor atomic migration/rollback. Import must independently validate schema/version, resolve dependencies and preview each destination operation before an explicit apply. A source ETag must never be reused as a destination write precondition.

Headers provide `Cache-Control: no-store`, the exact quoted source KV revision `ETag`, `X-RJS-Export-Scope: single-queue-declaration` and `X-RJS-Export-Omitted-Labels` count. Errors are JSON, not attachments: malformed/unknown/repeated query inputs return 400; missing declaration 404; inconsistent/unrepresentable declaration 409 `export_declaration_unavailable`; oversized output 503 `export_limit`. Limits: Queue name ≤256 bytes, encoded query ≤64 bytes, output including trailing newline ≤1 MiB, declaration read ≤3 seconds. No truncated success is returned.
